# 测试策略

本文件规定本项目的测试规则与实例。测试命令在 [`CONTRIBUTING.md`](../CONTRIBUTING.md) 的「质量门」小节；本文件不复制命令。

## 测试策略

测试过程与概念按 ISO/IEC/IEEE 29119-1:2022。变更级别由影响面决定：

| 级别 | 影响面 |
|---|---|
| R0 | 仅文档、注释、示例，不改变行为与契约 |
| R1 | 内部代码，不改变接口、数据、安全与部署 |
| R2 | 接口、协议、配置、数据展示、部署流程、界面行为 |
| R3 | 安全控制、数据删除、设备控制、供电、OTA、隐私 |

测试强度按变更级别确定：

| 级别 | 最低测试 |
|---|---|
| R0 | markdownlint 格式检查 |
| R1 | 单元测试 + 相关集成测试 + 全量质量门 |
| R2 | 单元、集成、契约、端到端关键路径 + 部署后验证 |
| R3 | R2 全部 + 安全测试 + 恢复演练 + 现场验证 + 分阶段发布 |

## 测试层级

| 层级 | 目标 | 范围 | 运行时机 |
|---|---|---|---|
| 单元 | 验证纯逻辑与边界 | 单个模块，无外部 IO | 每次提交 |
| 集成 | 验证模块与真实依赖协作 | 数据库、路由、协议编解码 | 每次提交 |
| 契约 | 验证三端与 Schema 一致 | 协议、OpenAPI、生成物 | 每次提交 |
| 端到端 | 验证关键用户路径 | 服务端 + 网页端 + 模拟设备 | 合并前 |
| 现场 | 验证真实设备行为 | 设备、网络、外部系统 | R3 与发布前 |
| 回归 | 防止已修复缺陷重现 | 缺陷相关路径 | 每次修复 |
| 非功能 | 验证性能、安全、可访问性、恢复 | 关键接口与界面 | 发布前 |

## 测试设计

1. 每条验收条件至少对应一个测试；无法自动化的必须有现场验证记录。
2. 边界与状态机使用等价类、边界值、判定表与状态迁移覆盖。
3. 时间、时长与时钟相关逻辑使用注入时钟与固定样本；不得依赖真实时间。
4. 重复投递、乱序、超时、断线、重启与部分失败必须有测试。
5. 缺陷修复必须先有能复现缺陷的测试，再修代码。
6. 测试名称说明行为与条件；失败消息包含期望值、实际值与输入。
7. 不得用重试掩盖不稳定测试；不稳定测试按本文「不稳定测试」一节处理。

## 数据与环境

1. 测试数据使用合成值或脱敏副本；不得使用真实学号、口令、令牌与个人信息。
2. 每个测试自建数据并清理；不得依赖其他测试的残留状态。
3. 测试不得访问生产环境、生产数据库或真实外部服务；外部服务使用受控替身。
4. 需要真实设备的测试必须记录设备型号、系统版本、网络条件与执行时间。
5. 测试日志与报告由持续集成保存；不得入库。

| 环境 | 用途 | 数据 | 访问 |
|---|---|---|---|
| 本地 | 开发与调试 | 合成数据或脱敏副本 | 开发者 |
| 持续集成 | 自动检查 | 合成数据 | 自动任务 |
| 生产 | 真实服务 | 真实数据 | 只读；不得运行测试 |

- 本地数据库可以删除重建；生产数据库不得删除重建。
- 生产数据进入本地前必须脱敏。

## 覆盖率

1. 覆盖率门槛在持续集成配置中定义，只升不降。
2. 覆盖率是下限，不是目标；关键分支必须有显式测试。
3. 排除项必须逐条说明原因；不得用全局排除掩盖未测试代码。
4. 新增关键逻辑不得降低覆盖率；覆盖率下降的变更不得合并。
5. 覆盖率数字由持续集成输出；文档不得写死。

## 缺陷管理

缺陷记录必须包含：环境、版本、复现步骤、期望结果、实际结果、影响面、证据、严重级别、责任人。

缺陷严重级别按 `CONTRIBUTING.md` 的「严重级别」。处置规则：

| 级别 | 处置 |
|---|---|
| S1 | 立即停止发布；修复后重新验证 |
| S2 | 发布前必须修复 |
| S3 | 当前迭代或下一迭代修复 |
| S4 | 排期修复 |

## 不稳定测试

1. 不稳定测试是缺陷，不是环境噪声。
2. 必须定位不确定性来源：时间、并发、网络、顺序、共享状态或随机数。
3. 修复方式是消除不确定性；不得用增加等待、自动重试或放宽断言掩盖。
4. 无法立即修复时，测试必须被隔离并记录责任人、原因与恢复日期；隔离不是删除。

## 安全测试

1. R3 变更必须执行威胁模型复核与针对性安全测试。
2. Web 端与设备端的验证标准按 `security.md` 选取适用条目；测试范围覆盖这些条目。
3. 必须覆盖：身份与授权、输入校验、输出编码、SQL 注入、命令注入、路径穿越、文件上传、敏感数据暴露、错误处理、依赖漏洞。
4. 依赖漏洞扫描按 `security.md` 的发布检查执行。
5. 安全测试证据写入发布记录；不得只写“已检查”。

## 可访问性

1. Web 界面必须满足 WCAG 2.2 AA。
2. 自动检查覆盖结构、标签、对比度与目标尺寸；人工检查覆盖键盘、焦点、缩放与屏幕阅读器。
3. 颜色不得作为唯一信息载体；错误必须同时有文字说明。
4. 可访问性问题按缺陷管理；阻塞关键任务的按 S2 处理。

## 性能与恢复

1. 关键接口必须定义时延目标与测量方法；变更影响性能时必须复测。
2. 设备命令必须验证超时、重试、重复回执与断线恢复。
3. 数据库必须验证备份、还原与完整性检查。
4. 队列与连接必须验证上限、背压与恢复。
5. 性能与恢复测试结果写入发布记录。

## 验收与证据

1. 验收由项目负责人执行；验收依据是变更单中的验收条件；验收结果写入发布记录。
2. 验收证据包括：测试报告、覆盖率、现场记录、部署后验证、监控截图或日志。
3. 未满足的验收条件必须列为未完成项；不得用“后续改进”代替验收。
4. 验收通过后，发布记录必须包含验收人、时间、版本与证据位置。

## 当前自动化范围

| 范围 | 框架与入口 | 说明 |
|---|---|---|
| 服务端 | pytest；`server/tests/` | 单元、集成、契约、接口与真实数据回放 |
| 设备端 | JUnit；`android/app/src/test/` | 纯逻辑、协议、时钟、队列、语音与设备状态机 |
| 协议契约 | pytest 与 Kotlin 测试；`server/tests/test_contract_sync.py`、`android/app/src/test/.../GeneratedContractTest.kt` | 生成物逐字节一致与三端动作集合对账 |
| 时间轴模型 | `tools/timeline_model/` 与 `server/tests/test_derivation_edges.py` | 参考模型与边界用例 |
| 网页端 | 浏览器手工验证 | 零构建静态页面；关键路径按可访问性与交互检查 |
| 现场 | 真机与生产只读观测 | 设备行为、网络、OTA 与外部系统 |

当前自动化范围只描述入口；测试数量与覆盖率数值由持续集成输出。

## 测试约定

- 测试不得使用 `sleep` 等待；异步等待使用事件、条件或受控时钟。
- 单条测试有 5 秒超时；超时表示用例在等待一个不会到达的事件。
- 每个用例自建数据并清理，不依赖其他用例的残留状态。
