## 方向二：长稳与可追溯（主体完成 0.4.4，剩余项按发现追加）

服务端与设备端的收尾，目标是**一次部署后长期免维护**：

- 安装后的文件清理：OTA 安装日志、发件箱、崩溃日志等各处落盘文件的
  上限与清理策略逐个核对（部分已有：crash.log 截断、outbox 上限、
  automation.log 截断——要清点的是"还有谁在写盘而没人管"）；
- 日志模块：服务端与设备端的日志口径统一（记什么、记多久、怎么取回）；
- 接口调用审计：`command_audit` 之外补齐 HTTP 侧的调用审计（谁、何时、
  调了什么、结果状态），与设备命令审计可关联；
- 长时间运行不积累垃圾：SQLite 体积（WAL、event 流水）、内存中的
  字典/缓存（挂起命令表、按设备分的帧锁）逐个核对增长曲线与上限；
- 回溯追溯能力：出问题时能按设备 + 时间段还原"当时发生了什么"
  （命令、状态迁移、配置变更、重启）。

## 方向三：统计层（待开工，清单与口径已定）

数据已经够了：**2026-06-22 起 100 天 + 实时**。但**目前没有任何读取方**——接口、页面、
报表都还没做。**不在这里写死条数**，它每天在变（见 `DECISIONS` 的原则）。

### 口径：按指标选数据集，不是一刀切排除异常

一次会话的真实时长 ≤ **1200 秒**（设备配置 `maxbatchtime`，满则强制释放）。由此分出四个
可用集，**判据都可从列上算出来，不落列**：

| 数据集 | 判据 | 用于 |
|---|---|---|
| 全量 | 无 | 出水类——`flow_s` 只累加有观测证据的段，从不高估 |
| 结束时刻可信 | `ended_at − last_seen_at ≤ 1200` | 占用 / 等待 / 利用率 / 时段类 |
| 盲区 | 同上取反 | 单列成表：采集断线率、可疑占用 |
| 超长占用 | `ended_at − assigned_at > 1200` | 单列成表：门被占着却一直不出水 |

**后两个不是一回事，别混。** 实测盲区那组只有个位数，而超长占用有一批——它们的
`last_seen_at` 紧贴 `ended_at`（盲区甚至为 0），也就是说每一帧都被看见了，只是**门被占着
却没有出水**。会话的结束只依赖"状态变成非占用"，没有任何时长上限；设备那条 20 分钟强制
释放管的是出水，管不了"刷卡不开阀"。做占用类指标时这一组会把均值拉偏。

### 调试账号：不排除

`cert_no = '99990052'` 是调试账号，频次与零出水率都远高于常人。**仍按普通用户统计**
——数据一致对待，它在报表上的影响看得见即可，不做特殊剔除。

**零出水会话全部保留**——那是真实的"刷了卡没洗"，是有意义的行为数据。

### 各维度能算的指标

**喷头**（`usage_session` 按 `door_no`，七个门都有数据）

| 指标 | 算法 | 数据集 |
|---|---|---|
| 使用次数、出水总时长 | `COUNT(*)` / `SUM(flow_s)` | 全量 |
| 平均每次出水 | `SUM(flow_s) / COUNT(*)` | 全量 |
| 占用时长 | `ended_at − assigned_at` 求和 | 可信 |
| 等待时长 | `opened_at − assigned_at` 求和（从占到开阀） | 可信 |
| 零出水率 | `flow_s = 0` 占比 | 全量 |
| 触顶比例 | `flow_s ≥ 1200` 占比（被设备强制释放） | 全量 |
| 短会话 | 出水时长低于某档的占比。档位由时长分布自己定——设备侧 `t_fastinoutdoorinfo` 只记 `(doorNo, 日期)`，阈值不在数据里，无从对齐 | 全量 |

**人**（按 `cert_no`，255 人）

每人次数与总时长、人均值、时长分布（直方图）、活跃人数、复访率（用过 ≥2 次的占比）、
使用间隔（同一人相邻会话之差）、偏好喷头（每人最常用的门）。

**时段**（按 `assigned_at` 的本地时间；**存的是 UTC，一律 +8 分组**，否则"晚上九点
高峰"会显示成下午一点）

小时分布、星期分布、按日与按月趋势、**高峰并发**（同一时刻处于占用态的会话数，区间
重叠计数）、时段 × 平均时长、工作日与周末对比。

**事件**（`door_state_event`）

暂停次数（数 `bathing→paused`）、恢复次数（数 `paused→bathing`）、暂停率（暂停次数 /
会话数）、报修次数与停用时长（数 `→repair` 与 `repair→` 之间的区间）、状态迁移全谱。
这类问题会话表答不了——它只覆盖"进入占用态到离开"这一条路。

**但统计层只读 `usage_session`**（见「记在最后」），事件表是另一条线，要用得单独开口子。

**设备**

| 指标 | 数据源 | 历史 |
|---|---|---|
| 断线次数、平均在线时长、在线率 | `device_link_event` | **只有 2026-10-02 起**，补不回来 |
| 数据完整度 | `door_snapshot` 的帧间隔分布 | **全量** |

**"这段时间为什么数据稀"用帧间隔就能答**，不必依赖在线率——后者要等它自己攒。

**异常**

**两组，判据不同、成因也不同**（见上面的四数据集表）：跨盲区那组是采集断线，比例与盲区
时长分布按日按月看；超长占用那组是门被占着却不出水，跨度超过 1200 秒的单列。

### 两处已经定了的口径

**利用率的分母不选定一个，全部并列输出。** 同一件事有几种算法就出几个名字：出水、占用、
等待、占着没出水各成一列，比率的分母写在页面上。不做"选一个口径"的取舍——那等于替使用者
决定他看到的是什么。分母候选（占用时长除以什么）：

- 有数据的时段（首场到末场）——随使用时间自然伸缩
- 每天的实际开放时段（首次使用到 23:53 自动清理）——贴近真实可用时间
- 固定值（如 6:00–23:53）——便于跨日比较，但把没人来的时段也算成"可用"

**查询层面不建汇总表**，直接查明细：明细按年计也就几万行，而汇总必然与明细漂移。

### 记在最后

统计可以慢慢做，**但明细必须从第一天就在**。原始帧全量落库、派生结果单独立表，
口径将来怎么改都能重算——这是先落原始层的全部意义。

**统计层只读 `usage_session` 这一张表**：不碰原始层，也不碰事件表。数据来源单一时口径
才不会分叉；需要事件表的那些指标（暂停次数一类）要另外开口子，不混进这一层。
