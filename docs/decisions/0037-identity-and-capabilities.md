# 0037. 用户面访问控制：身份标识 + 能力位

* 状态：accepted（取代 0034 中"用户面操作接口匿名"的部分）
* 日期：2026-09-30

## 背景与问题

0034 决定用户面操作接口匿名——那是对齐旧系统（ntu-remote-shower）的结论，理由是
"学号+密码只是转发给浴室系统的业务凭证，真正的验证在浴室端"。

但产品目标里明确有三类使用者：**未授权只读**、**授权用户可分配/结算/拍照**、
**管理员改配置**。匿名方案里"授权用户"这个角色根本不存在，任何人都能调用
assign/settle/photo。

## 考虑过的选项

* 保留匿名（0034 现状）——无法表达"谁能操作"
* 完整 RBAC + JWT + 用户表——0034 刚废掉，且用户明确要"最简单，请求带一个标识"
* **身份标识 + 能力位**（采纳）
* 复用 status-panel 的 openid 白名单——语义对，但名单在配置文件里，后台改不了

## 决策结果

调用方在 `X-Identity` 头携带标识，服务端查名单得到能力位：

* **小程序**：`wx.login` 的 code → 服务端换 openid → 直接返回 **openid 本身**作为标识
  （不再包一层会话令牌：openid 由微信签发、稳定不变，加一层只会引入过期与重登）
* **网页**：管理员签发一个不透明标识（网页拿不到 openid，标识本身即身份）
* **能力位**：`ops`（分配/结算）、`photo`（拍照）；名单存数据库，后台可增删
* **管理面不变**：仍用 `X-Admin-Token`，名单改动只应来自运维通道

### 正面后果

* 三类使用者可表达；查看类接口仍无需任何凭据
* 语义与 status-panel 已验证的方案一致，两套系统的心智模型统一
* 无会话、无过期、无令牌刷新——撤销靠从名单删掉

### 负面后果

* openid 可被冒充（需先拿到它：反编译小程序 + 该用户授权）；
  但操作还需浴室账号密码，冒充者拿不到这一层
* 网页标识是长期有效的 bearer，泄露即失守；缓解是可在后台即时撤销
