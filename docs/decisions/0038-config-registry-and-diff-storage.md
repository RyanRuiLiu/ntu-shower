# 0038. 远程配置：登记表 + 只存差异

* 状态：accepted（取代 0021 的"14 项固定键集"与"存合并快照"）
* 日期：2026-09-30

## 背景与问题

0021 用一份扁平的值字典管理配置，键集固定 14 项，存储时把"默认值 + 改动"合并成
**完整快照**入库。三个后果在生产上真实发生：

1. **设备覆盖冻结全局变更**：快照固化了当时的默认值，此后改全局对已有覆盖的设备
   完全无效。实证：全局把 heartbeat 改成 20 后，有覆盖的设备仍读到 30、无覆盖的
   设备读到 20——同一配置两台设备行为不同，且无任何提示。
2. **生产库停在 14 键的旧版本**：后加的 7 个键（崩溃守护 4 个、自动结算 3 个）
   从未出现在下发给设备的配置里，设备一直靠本地默认值兜着。
3. **入参无校验**：未知键静默丢弃（提交成功却什么都没发生）；`heartbeat_interval_s = 0`
   可原样下发，设备会立刻重发心跳形成风暴。

## 考虑过的选项

* 维持扁平字典 + 加一层校验——治标，快照问题仍在
* **带元数据的登记表 + 只存差异**（采纳）
* 引入配置中心/外部 KV——规模不匹配

## 决策结果

* `modules/config/spec.py` 登记每个键的类型、范围、单位、归属（device/server）与说明。
  **新增键只改这一处**，服务端校验、客户端渲染、文档生成皆由它派生。
* 存储改为**只存与默认值不同的项**；`effective` 每次按 `默认 ← 全局 ← 设备` 现算。
  调用方提交整个表单也不会把未改动的键固化成覆盖。
* 入参经校验拒绝未知键、类型不符与越界值（422 `invalid-config`）。整数校验显式排除
  `bool`——它是 `int` 的子类，不排除会让 `true` 通过。
* `GET /admin/config/spec` 暴露登记表，客户端据此渲染控件，不再各自硬编码键表。
* 设备端**不重复**服务端的业务范围（两处各写一份必然漂移），只兜"失控"：
  0 或负数的时长会让 `postDelayed` 立即触发，一律抬到至少 1。

### 正面后果

* 改默认值即刻对所有设备生效；加配置键只改一处
* 非法值在入口被拒，不再需要靠设备端容错
* 两端键集合由 `test_config_spec.py` 对账（解析 Kotlin 源码提取，防单边漂移）

### 负面后果

* 有效配置每次现算，多两次字典写入（单机规模下可忽略）
* 设备端仍需一层下限兜底：纵深防御，防配置经旧版服务端或手工干预进入
