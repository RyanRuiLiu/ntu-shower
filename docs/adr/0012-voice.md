# ADR-0012: 语音播报的控制边界与时间口径

- 状态：Accepted
- 日期：2026-10-30（整理入档；原始决策日期见 Git 历史）
- 决策者：项目负责人
- 取代：无

## 背景

本条目汇总该领域的有效决策；原始讨论、实测与取舍见相关代码注释、`docs/adr/` 的 evidence 附录 与 Git 历史。

## 决策

- **配置面在服务端，播放面在设备端**：服务端保存固定音频素材与规则、派生事件、按固定优先级
  匹配，并把规则分段按事件值解析成播放清单下发 `voice.play`；设备只负责下载/校验、按指定
  音量顺序播放、结束后恢复原音量。设备不保存规则、不判断事件、不做语音合成。
- **规则目标是设备、学号与时段**：设备与学号都可以写 `*`（全部设备 / 全部学号）；匹配
  优先级沿用「设备具体 > 设备通配 → 学号具体 > 学号通配 → 同档内设备集合更小者优先，
  再比学号集合」，最后才比时段：有时段 > 无时段，覆盖分钟数更少 > 更多。时间只在前四项
  完全相同时参与，不会越过设备/学号的具体性。规则 id 不参与决胜——它只是写入顺序，
  不是业务优先级。保存时拒绝优先级完全相同且目标、时段都相交的同事件规则；时段不重叠
  可以共存。要临时换播报内容，停用规则或调整目标范围。原有优先级字段随此模型移除。
  「全部学号」的规则可带**排除名单**：名单里的学号不命中这条规则，让位给次特异的
  候选（没有就不播）。排除只作用于那一条规则、只对「全部学号」有意义——具体学号的
  规则把目标自己排除掉等于停用，那种形状直接拒绝。
- **`assigned` 是会话生命周期事实，其余事件是观测到的状态迁移**：新会话一建立就产出
  `assigned`；`startup` 全貌帧和盲区帧只要 `open_time` 能平移（`source=inferred`），
  也用真实分配时刻补发，不再因为“不是 db_watch 帧”而丢掉。没有 `open_time` 的观测
  下界不补——不知道什么时候分配的，补了就是编时刻。`shower_started` / `paused` /
  `resumed` / 释放事件仍只从实时 `db_watch` 观测迁移产出；历史重放不补播。换人只
  为新学号产出 `assigned`，不为旧学号产出释放事件。释放按**释放前最后一帧的占用
  状态**拆成三种：未开阀释放 / 淋浴后释放 / 暂停中释放——“本次淋浴 X 分钟”只对
  淋浴后释放成立。事件中文名取 `DoorState` 的目标状态正名（等待开阀 / 淋浴中 /
  已暂停 / 空闲），不另造动词；选择界面按 分配 / 用水 / 释放 三阶段分组勾选，
  规则在设备、学号、事件三个轴上分别选。
- **规则是固定素材的分段序列，不是文本模板**：每段只能是 `asset`（素材库里的固定
  音频）、`digits`（数字变量）或 `pause`（100–5000 毫秒静音）。`digits` 的语义由来源
  决定：`door_no` 是数值，按中文数词读，数字取 0–9、十/百/千/万取单位素材；
  `cert_no` 是标识，逐位读，只取数字字符（结尾字母等非数字自然忽略），可截取末 N 位。
  位置与间隔完全由分段顺序表达；没有文本、音色、语速或实时合成。数字与单位素材
  全库唯一，缺任何一位/一个单位就不能保存使用它的规则。支付状态、金额、姓名没有
  可靠数据源，不做。
- **时段的判定轴是服务端当地时间**：规则可带多个每周重复的时段，跨天按开始日算，
  包含开始、不含结束；按 `extend_hours_zone_offset_minutes` 的固定偏移换算，不读取
  设备墙钟（设备钟会被延长服务拨快），也不做节假日/具体日期。人工预览与推送不检查
  时段，自动事件才检查；没有命中的规则就不播，不另造默认规则。
- **素材以内容哈希为身份**：上传的源音频在服务端统一转成 44.1k 单声道 MP3，文件名就是
  归一化后的 SHA-256；同一段音频换名字上传不会生成第二份文件。素材被规则引用时禁止
  删除（停用的规则随时会再启用），改名只影响展示名。素材与 `data/` 一起保留。
- **规则保存即向在线设备预下载素材，但预下载不占播放通道**：服务端把规则用到的素材
  （含数字 0–9，以及 `door_no` 用到的十/百/千/万单位）一次性发 `voice.prepare`，并把它划入独立的 prefetch 通道（与 voice
  播放通道分开排队）；设备立即确认，把清单交给独立的后台线程逐段
  下载到应用私有目录。播放开始时后台预下载暂停并取消当前 HTTP 调用，把带宽让给播放，
  结束后再继续；每段之间留出让路窗口，网关心跳与帧回执不被饿死。设备断线或未受信任时
  预下载暂停，重连后再继续。预下载完成后，事件到来时直接命中缓存。播放时缺失素材的下载另有
  60 秒总预算，超时即失败返回，不无限占住语音队列；0.1 Mbps 链路上一条 30 秒素材约
  38 秒，预算覆盖单段下载但不会让整条通道卡死。若首次事件发生在预下载完成前、且
  整条清单的下载超过这个预算，本次播报失败并留下投递记录，后台预下载继续，后续事件
  再命中缓存。设备缓存按内容哈希复用、只保留在
  `filesDir/voice`，不进共享存储；升级时删除旧的 `/sdcard/ntu-shower/voice`，中断
  留下的 `.part` 与超限旧文件在启动时清理。
- **等待浴室 App 的提示音在设备端完成**：浴室 App 的分配/结算提示是 `MediaPlayer`
  播的预录音频，走 `STREAM_MUSIC`；本应用播报走 `STREAM_VOICE_CALL`，两边都不抢
  音频焦点，同时播就会混在一起。设备在播放前用 `AudioManager.isMusicActive()` 检测
  浴室提示音，等它结束再开口；最长等待由设备端常量 `VOICE_BATH_WAIT_MAX_MS` 控制
  （15 秒），超时照常播放
  并记 `audio.bath-wait-timeout`。规则没有逐条延迟；投递记录保存下发/完成时刻与
  是否现场下载，网页「最近推送」据此排查。自动结算/续期/延长服务产生的释放与
  重新分配仍按事件处理，靠规则配置规避重复，不另设来源抑制。
- **播放清单在设备端合成一条 PCM**：预下载的 MP3 在本地解码成 44.1k 单声道 PCM，
  去掉每段开头的编码器延迟/静音并保留 10ms 起音，再写入同一条 AudioTrack；停顿
  写成精确静音。这样数字与短语之间不再有逐段新建 MediaPlayer 的缝隙。解码失败按
  播放失败处理，不改变预下载与事件时零网络的边界。
- **手动推送与自动触发共用一条投递链，来源由事件键区分**：管理台的「推送」按规则
  同一条解析/下发路径真播一遍。投递记录不另存来源列：`manual:*` 事件键已经是
  「谁发起」的身份，页面据此显示自动触发或手动推送。
- **离线不播、不排队、不补播**：事件超过 60 秒（服务端常量 `VOICE_EVENT_MAX_AGE_S`）就跳过；
  同一事件用 `event_key` 只认领一次。素材按内容哈希缓存，设备端有容量上限与最旧淘汰。
- **设备走 `STREAM_VOICE_CALL`**：本机实测只有这条流在主输出上有非零音量（4/5），
  Media/TTS 流为 0；播放前保存并设置该流音量，结束/失败/超时后恢复，进程被杀时由本地
  待恢复标记在下次启动时补恢复。设备日志用 `audio.*` 事件名，`voice.*` 只留给命令失败原因码。
