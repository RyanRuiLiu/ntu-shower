# ADR-0020: 设备接入采用 claim 自注册（fleet provisioning by claim）

- 状态：Accepted
- 日期：2026-11-09
- 决策者：项目负责人
- 取代：切换清单里的「令牌逐台写进设备」预埋步骤

## 背景

设备接入令牌强制校验后，设备侧必须有凭据才能连上服务端。原计划在停机窗口用转换工具签发明文、逐台写进设备——6 台分布在不同楼层，物理接触成本高；且设备零界面（ADR-0007），「首次连接引导」不成立。

## 决策

采用行业标准的 claim 自注册模式（AWS IoT fleet provisioning by claim / Azure DPS 同型）：APK 构建期内置一枚全队共享的 claim 令牌（gradle property 注入，不入库），任何设备装上后首次连接调 `POST /api/v1/devices/enroll` 换每台自己的接入凭据（注册即轮换：吊销旧凭据、签发新凭据），落应用私有目录，此后 WS 握手带 `Authorization: Bearer`。信任位照旧由管理员在档案上点——注册只回答「这是本应用的程序」，ADR-0007 的信任模型不变。

## 备选方案

- 逐台预埋（device.exec 写令牌/物理 adb）：未选——手工舞步、不可扩展，且「装到任何设备都能连」是明确的用户诉求。
- 注册后即信任：未选——信任位是 ADR-0007 的安全边界，注册通道的凭据强度（APK 内置共享令牌）配不上它。

## 后果

- 正面：装上即连，新设备零构建成本；重装 APK/清数据自助恢复；claim 泄露的轮换只影响 APK 重新构建，库内已签发凭据不受影响。
- 负面：claim 令牌可从 APK 逆向提取——伪造设备可完成注册。该风险与 ADR-0007「设备自有、伪造需物理接触」同级（APK 分发本身受控），信任位把关；出现第三方分发 APK 的场景即重启此决策。
- 转换工具的 `--token-output` 退为可选运维通道，切换清单不再依赖它。
