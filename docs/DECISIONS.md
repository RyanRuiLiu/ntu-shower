# ntu-shower 决策记录

本文件是唯一一份决策记录。原 `docs/DECISIONS.md` 下的 40 份 ADR 已合并到此，编号不再维护：
被后续决策取代的部分只保留当前有效的结论，一次性过程不入档。

每条写"现在约束代码的是什么"与"为什么"。协议字段、配置键、错误类型、动作名的具体值与说明
在代码与 `protocol/schema/` 里，此处不复述。

## 总体取向

- **措辞禁令见 `AGENTS.md`**：被禁的那几个词描述的不是文风，而是一种设计——假定主方案不完整，
  再补一条次等的。本项目取向相反：每条通路各自完整、按场景选。由
  `server/tests/test_language_rules.py` 强制，豁免位置登记在该文件内，新增豁免必须写明理由。
- **不写兼容代码与数据迁移**：项目未上线，数据库直接删表重建，schema 只有最初版本。
  结构变更必须同步改调用方；收益是仓库里不存在只在旧数据上成立的暗角。
- **不留无用物**，但"当前无人读取"不等于无用：`usage_session`、`door_state_event`、
  `command_audit` 是统计口径的原始数据，删了不可复得，必须先攒。
- **一改一验**：改完立刻跑门禁，不攒一批再验。命令超过 10 秒说明有问题——测试有 5 秒单例超时，
  超了就是它在等一个永不到来的事件。
- **能简则简**：一个域名、一个端口、一张证书、一个服务进程。少一个组件就少一处会坏的地方。
- **换服务器 = 只改 DNS 记录，零现场**。这条是上一条的推论：没有要改的配置项，就没有上门的理由。

## 时间轴：两条铁律

> 两条轴的定义、三条换算规则、哪个字段属于哪条轴，都在 `docs/ARCHITECTURE.md`「时间轴与口径」
> ——那里是它们的**唯一规范**。这里只记"为什么这么定"与踩过的坑，不复述定义。

- **两条轴的解析函数不可混用**：混了不报错，只是数字归零或偏一整个量。这个错误在本项目里
  犯过两次（一次在推导里，一次在"从设备痕迹推回开阀时刻"里），两次都是静默的——
  `tests/test_derivation_edges.py` 里那几条边界用例就是为它们留的。设备钟的**绝对值**不可信
  （自然漂移 8.5 秒/天，100 天里 16.6% 的锚点落在被改过的时段），而它的**差值**可信：两个
  读数出自同一口钟，差值与被拨动多少无关。
- **对外字段一律在服务端轴上**，设备报的原话只留在原始帧。同一个字段名在两处放两条轴的值，
  读的人分不出来，而"形状相同、含义差一个偏差"比"没有值"危险得多：`door_live` 的三个时间
  字段曾按设备轴存，网页于是把分配时刻渲染成 `00:55`、还把 `|时刻 − 本地时间|` 当已洗时长在计。

## 数据分层：五张表

- **原始层与派生层分开**。`door_snapshot` 是设备说了什么就记什么；`door_live` 现态、
  `door_state_event` 状态迁移、`usage_session` 一次占用、`usage_segment` 一次连续出水都是推出来
  的。**规则改了历史就得跟着重算**，没有原始帧就永久无法重算——旧系统只留了原始帧，那 100 天
  今天才能重放回来。代价约 170MB/年，换来"任何改动都可重放"。
- **段与会话分开**，因为粒度不同：会话是"一次占用"（人 + 门 + 起止），段是占用里的一段连续出水。
  合成一张就把"洗一次"与"开了几次水"压成一件事。段的长度取"同一口钟上两个读数之差"，比会话级
  的合成稳健——早先那条 `max(bathTime, 上一帧 + 间隔)` 一把抓的公式把暂停那一帧的间隔重复算过
  一遍，100 天里有 1,422 条会话因此偏大，合计 2,011 秒。
- **段长要分档**：它可能来自设备那口钟的两个读数之差（精确），也可能只能靠我们的观测（含帧
  间隔与采集延迟），还可能被截断、或从设备留下的痕迹推回。**必须分开**，否则统计会把"我们
  不知道有多长"当成"就那么长"。**取值与判定在 `usage_segment` 的建表注释里——那是唯一出处。**
- **交叉校验会误判，如果两个差不同起点**：设备轴差与观测差只有在"段起点就是设备报的 `in_time`
  平移来的"时才可比。平移失败时观测差的起点退回了帧时刻，它会偏小，拿它去否决设备轴差就错
  了——后者是同一口钟上两个读数之差，根本不依赖平移。判据与处置在 `service._close_segment`。
- **"完整"不能用推出来的长度自证**：`derived` 段的长度就是从设备那个值推回去的，等式必然成立，
  拿它当完整的证据是循环论证。而设备那个值本身可能被拨钟放大。
- **盲区要切开会话，不能当成连续**：设备那条 20 分钟强制释放管的是出水，管不了"喷头被占着不
  出水"；不切的话，库里的陈旧占用会被读成"它还被占着"，那场会话永不结束、起点落在几小时前。
- **可推导的不存**：结束原因是编造的（主动出门与四种超时释放写的是同一套清零 SQL，
  `bathing→free` 与 `paused→free` 完全同形），暂停次数数 `door_state_event` 的 `bathing→paused`，
  出水次数数段，各类时长都是几个时刻的差。**不建汇总表**——明细按年计也就十万行量级，而汇总
  必然与明细漂移。

## 统计层：口径与数据集

- **按指标选数据集，不是一刀切排除异常**。一次会话的真实时长不超过设备的强制释放阈值
  （`service.SESSION_MAX_S`，它的来源是浴室 App 的 `maxbatchtime`——那个值不在本仓库），
  由此分出四个可用集，**判据都能从列上算出来、不落列**：
  - **全量**：出水类。`flow_s` 只累加有观测证据的段，从不高估；
  - **结束时刻可信**：`ended_at − last_seen_at` 不超过那个阈值。占用 / 等待 / 利用率 / 时段类；
  - **盲区**：上式取反。单列成表：采集断线率、可疑占用；
  - **超长占用**：`ended_at − assigned_at` 超过那个阈值。单列成表：门被占着却一直不出水。
- **后两个不是一回事**。实测盲区那组只有个位数，而超长占用有一批——它们的 `last_seen_at`
  紧贴 `ended_at`（盲区甚至为 0），也就是每一帧都被看见了，只是**门被占着却没有出水**。
  会话的结束只依赖"状态变成非占用"，没有任何时长上限；设备那条 20 分钟强制释放管的是出水，
  管不了"分配不开阀"。做占用类指标时这一组会把均值拉偏。
- **利用率的分母不选定一个，全部并列输出**：同一件事有几种算法就出几个名字——出水、占用、
  等待、占着没出水各成一列，比率的分母写在页面上。不替使用者决定他看到的是什么。
- **查询层面不建汇总表**，直接查明细：明细按年计也就十万行量级，而汇总必然与明细漂移。
- **调试账号（`cert_no = '2530110052'`）不排除**：它的频次与零出水率都远高于常人，但**数据
  一致对待**——它在报表上的影响看得见即可，不做特殊剔除。
- **零出水会话全部保留**：那是真实的"刷了卡没洗"，是有意义的行为数据。
- **明细必须从第一天就在**：原始帧全量落库、派生结果单独立表，口径将来怎么改都能重算。
  这是先落原始层的全部意义。

## 架构与模块

- **设备端定性为寄生在设备上的程序**，只做三件主功能：读浴室 App 数据库的 `t_doorlist`、经无障碍服务操作
  其界面、维持自身存活（自更新/看门狗/崩溃自启）。浴室 App 无导出组件、`uiautomator` 永不空闲
  且自身会崩，替代它没有路径；把主功能定死是为了挡住功能蔓延，其余全部算扩展。
- **服务端是 FastAPI 模块化单体，单进程单事件循环**。I/O 密集的长连接聚合在单事件循环下模型
  最简单；代价是垂直扩展受限，需要拆分时按事件总线接口换实现，业务代码不动。
- **按领域拆模块，各模块自带 `router` 与 `admin_router`**。两者都挂在 `/api/v1` 下，区别只在
  `admin_router` 多一层 `require_admin` 依赖——**管理面不是靠路径前缀隔开的**，所以不存在
  "哪里是管理台"这一层。设备、喷头、会话、配置、身份、桥接、OTA、审计各自持有自己的路由，
  新增功能有确定落位。
- **网关平面与领域平面分离**：`gateway/` 只负责设备 WS 长连接的生命周期与分发，业务状态由
  `modules/` 各自持有并落库。
- **实时推送走进程内事件总线**（`core/events.py`）。单进程下零额外依赖；接口按可替换为
  Redis pub/sub 的形状设计，拆分进程时才需要动它。
- **设备影子（`modules/shadow`）是扩展功能的统一读写入口**，reported / desired / metadata 三段，
  对齐 AWS IoT Device Shadow。扩展只面向影子编程，不直接查表。
- **同一 APK 装所有设备，设备档案集中在服务端 `devices` 表**。新设备零构建成本，OTA 只维护
  一个版本；代价是设备身份与档案都在服务端。

## 协议与契约

- **协议承载在 WSS 上，载荷是 JSON 信封**，类型名点分（`link.hello`、`session.command`）。
  设备量级下 protobuf/MQTT 的复杂度换不来收益，而抓包即读、schema 即文档。
- **字段与类型全套规范化**：字段 `snake_case`、RFC3339 时间、UUIDv4 消息 id、每个 type 一份
  JSON Schema。三端同源无歧义，新增可选字段不升版本号。
- **信封只有一处组装**：服务端 `core/protocol.py`、设备端 `MessageCodec`。所有出站帧经它们
  构造，协议格式改动只改一处；错误帧是扁平的 `{code,message}`。
- **JSON Schema 是协议的唯一事实源**，存 `protocol/schema/`（含 `envelope.json`），CI 按样例
  校验。改协议必须三处同步：schema、服务端实现、设备端实现。
- **HTTP 错误统一为 RFC 9457 Problem Details**：`application/problem+json` 的
  `{type,title,status,detail}`，由 `core/errors.py` 装配（含 422 校验错误）。`type` 是 kebab-case
  的稳定 code，登记在 `core/problems.py` 且一经发布不改；`title` 是中文展示文案、`detail` 承载
  可变信息。客户端按 `type` 分支，不解析自由文本，也不在前端另维护一层文案映射。
- **设备在 `link.hello` 声明自己支持的 action 集合，服务端下发前比对**，只在声明的范围内下发。
  空数组表示未声明（升级前的旧版本），此时不拦截——否则升级服务端会把在网设备锁死。
- **配置经 `link.hello_ack` 与 `config.update` 下发合并后的有效配置，未知键设备忽略**。
  新增配置键不影响旧设备，靠"忽略不认识的键"实现。
- **喷头状态是受约束的枚举而非裸字符串**：`DoorState`（`modules/doors/schemas.py`）由设备上报的
  4 个原始整数派生，定义成 `str, Enum` 让 OpenAPI 生成 `enum`，客户端据此生成联合类型，
  不必手抄一份状态清单。
- **动作名与失败原因码是封闭集合**，登记在 `core/actions.py` 与 `core/reason_codes.py`，
  各有一份测试对账。两端各写一份字符串迟早会对不上，对不上时出错的是现场设备。

## 设备端

- **设备身份 = `ANDROID_ID`，服务端人工点信任后才通信**。重装 APK 身份不变，恢复出厂等于重新
  认领一次——现场零输入、无配对窗口期。代价是 device_id 即身份、没有第二凭据；设备自有，
  伪造需物理接触目标设备，接受。
- **设备零界面、零本地配置**：无 Activity、无桌面图标、无最近任务，一切运行参数由服务端下发。
  现场没有可误配的操作面；代价是设备完全依赖服务端可用性。
- **网络锚点与 TLS 都按设备实测能力定**：系统 DNS 被校园网封锁、TLS 上限 1.2、可用套件只有
  CBC 系列——这些都是**设备侧的事实**，写在 `docs/ARCHITECTURE.md`「已定稿的传输层事实」里。
  这里的决策只有一条：**不为迁就设备而加垫层**，该显式放行就显式放行（`transport/GatewayClient.kt`），
  而不是写一段"失败就换个套件重试"的代码。
- **占用判定用 `cardno` 与 `accno` 组合**：`cardno != 0` 或 `accno` 非空非 0 即占用，
  `status` 字段实测不可靠。无卡模式（`cardno=0`）的占用者落在 `certno`/`accno`，
  只看 cardno 会漏判。
- **`FileObserver` 掩码必须含 `MODIFY`，事件按 1 秒防抖合并**。浴室 App 长持数据库 fd 不关闭，
  事务写入只触发 MODIFY、不触发 `CLOSE_WRITE`；只监听后者的实现会静默漏报，代价是 1 秒延迟。
- **崩溃守护是参数化的扩展功能**，不是地基：开关、冷却、阈值经配置下发。浴室 App 会自崩、
  需要拉起，但参数写死在设备端就无法按现场调整。
- **构建工具链能新则新，运行时冻结在 4.4**：Gradle 9.8 + AGP 9.4 + 内置 Kotlin + JDK 25，
  `minSdk`/`targetSdk` 19 不随工具链上升。设备 ROM 无升级路径，但构建侧没有理由停旧；
  代价是 lint 长期豁免 `ExpiredTargetSdkVersion`。

## 身份与能力

- **统一身份制，全部凭 `X-Identity` 头**：查看类接口无需凭据；用户面按能力位
  （`session` 分配/结算、`photo` 拍照）+ 设备作用域判定；管理面（截图、远程执行、
  配置、名单、发布、审计）要求 `admin` 能力位。没有独立的运维令牌通道——管理台
  也是"一个带标识的调用方"，同一套判定、同一份审计。权限本身就是能力位，不存在
  "这个人是什么角色"这一层，也就没有按角色下发不同内容的分支。早期的三级角色
  模型（只读/用户/管理员）与后来的 OPS_TOKEN 运维令牌均已废除。
- **能力位与作用域双维判定**：能力回答"能做什么"，作用域（`["*"]` 或设备 id 列表）
  回答"对哪些设备做"。授予记录存数据库、后台身份页可改，改动即时生效（每请求实时
  查库）；撤销即从名单删除。名单里的标识按来源分 `openid`（小程序）与 `web`
  （我方签发）两种，同一种资源、同一份名单。
- **本项目不含微信交互**：`wx.login` 的 code 换 openid 在 status-panel 完成；
  openid 由微信签发且稳定，本项目直接认 openid 字符串为身份，不另发会话令牌。
  网页标识是管理员签发的不可枚举随机串，本身即身份。
- **不建用户身份体系**：`users` 表、JWT 签发、令牌端点一律不引入——真正的凭证校验在学校
  那侧，自建身份对用户是多余步骤，也少了用户数据这份攻击面。
- **浴室凭证存在后台任务名单里**（明文）。三份名单各是 `学号=密码` 一行一个——**凭证跟着
  名单走**，所以"在名单里"与"有密码"是同一件事，不存在"名单里有他、却没有密码"那种静默
  不执行；代价是同一个学号开两个功能要在两份名单里各写一遍，那是刻意的：配一份读得懂一份。
  只有被显式写进某份名单的学号才有这一条。
- **密码哈希直接用 `bcrypt` 官方库**（`hashpw`/`checkpw`），不经 `passlib` 包装。
  `passlib` 1.7.4 与 bcrypt 4.1+ 不兼容是已知问题，直接调官方接口没有这层维护成本。
- **后台任务的每一次终局都落一行，永久保留**（`background_task_run`）。它在帧上动手、
  没有任何 HTTP 请求在途，按审计那条口径就该自己留一行；而它记的是"决定"（哪个功能、
  当时阈值多少、为什么动手或没动手），与"发了一条什么命令"不是同一件事。保留期上它与
  两条审计流水**不同**：`core.audit.prune` 只清 `api_call` 与 `command_audit`，这张表
  不进清理名单——效果本身留在 `usage_session` 里，"为什么、第几次"只有它说得出来。
  量级也支持：每个动作必先下发一条命令，所以不会超过 `command_audit` 那个量级（实测约 2 条/天）。
- **资源约束按真实功能设计，不用通用 QPS 限流**：同一设备的第二条在途命令直接 409
  `device.busy`，不排队；OTA 上传体积上限入配置。这样把正确性与资源保护合成一件事。

## 远程配置

- **配置键登记在 `server/app/modules/config/spec.py`**：每个键的类型、范围、单位、归属
  （device/server）与说明都在那里。新增键只改这一处，服务端校验、客户端渲染、接口文档都从它
  派生。
- **只存与默认值不同的项**，`effective` 每次按 `默认 ← 全局 ← 设备` 现算。存合并后的结果会把当时
  的默认值固化进设备覆盖，此后改全局对已有覆盖的设备完全无效——生产上真实出现过两台设备读
  同一份配置却行为不同，且没有任何提示。
- **入参校验拒绝未知键、类型不符与越界值**（422 `invalid-config`），不再静默丢弃。
  整数校验显式排除 `bool`——它是 `int` 的子类，不排除会让 `true` 混过数值范围检查。
- **`GET /api/v1/config/spec` 暴露登记表**，客户端据此渲染控件，不各自硬编码键表；两端键集合由
  `test_config_spec.py` 解析 Kotlin 源码对账，防单边漂移。
- **设备端只做失控下限保护，不重复服务端的业务范围**：0 或负的时长会让 `postDelayed` 立即
  触发，一律抬到至少 1。两处各写一份业务范围必然漂移，数值边界只由登记表定义。

## 屏幕提示的控制边界

- **配置面在服务端，显示面在设备端**：服务端只下发文字、样式、位置、条件与总开关；
  “此刻显不显示”由设备端 `NoticeRule` 一处判定。不新增 show/hide 消息——服务端判定会把
  “当前占用”变成服务端缓存，把时间边界变成每台设备每分钟一次的下行消息，而设备离线时
  显示会停在断开前。服务端仍是配置的唯一来源，改 `notice_enabled=false` 并推送即可在线
  关闭。
- **时间条件用服务端时间轴，不用设备墙钟**：设备通过 `link.hello_ack` / `link.ping`
  建立 `ServerClock` 锚点，再用单调钟外推；本地星期与当天分钟用设备系统时区换算。
  服务端时间锚点取不到（进程刚启动且未连上）时时间条件未决，按隐藏处理。延长服务期间
  设备表盘可能被拨快跨日，而提示按真实服务端时间判断——两者会不一致，这是选择真实时间
  的直接代价。
- **占用条件用设备本地 `t_doorlist`，不用服务端 `door_live`**：设备直接读产生上报帧的
  同一次数据库变化，天然比服务端缓存新；断网时同样可读。读数为空、退出码失败或任一行
  坏掉都算不完整，占用条件隐藏，不把空读当成 0 个占用。占用只随 DB 事件更新，
  不做固定间隔轮询——每 30 秒多 spawn 一次 `sqlite3` 只是无谓 IO。
- **窗口沿用 `TYPE_PHONE + SYSTEM_ALERT_WINDOW`**：与 `CoverOverlay` 同一套在本 ROM 上
  验证过的组合，不引入 `TYPE_SYSTEM_OVERLAY` 等未验证类型。提示窗不可触摸、不可聚焦，
  x/y 以整块屏幕为原点；操作遮罩显示期间提示窗被移除，避免依赖“同类型窗口后加的在上”
  这种并发下不成立的经验。
- **无障碍事件按包名隔离**：提示窗的窗口/文字事件属于本应用，不能当成浴室 App 退出或
  页面变化；`A11yService` 直接丢弃本包事件，提示视图也不进入无障碍节点树。

## 语音播报的控制边界与时间口径

- **配置面在服务端，播放面在设备端**：服务端保存规则、派生事件、按特异度匹配、合成音频并
  下发 `voice.play`；设备只负责下载/校验、按指定音量播放、结束后恢复原音量。设备不保存
  规则、不判断事件、不做语音合成。
- **规则目标是两个维度，各自具体或「全部」**：设备与学号都可以写 `*`（全部设备 / 全部
  学号）；匹配时具体压过通配——先比设备维度、再比学号维度。「设备 × 学号 × 事件」有唯一
  约束：一个目标只有一条规则，匹配结果因此确定，不需要优先级字段（原有优先级随此模型
  移除）。要临时换播报内容，停用具体规则让通配顶上，或直接改文本。创建按「设备集合 ×
  学号集合」展开（上限 500 条），已存在的组合跳过并在响应里点名，重复提交幂等。
  「全部学号」的规则可带**排除名单**：名单里的学号不命中这条规则，让位给次特异的
  候选（没有就不播）。排除只作用于那一条规则、只对「全部学号」有意义——具体学号的
  规则把目标自己排除掉等于停用，那种形状直接拒绝。
- **事件只从实时 `db_watch` 帧派生**：`startup` 全貌帧、历史重放、首帧、盲区前后、
  换人都不补播；换人只为新学号产出 `assigned`，不为旧学号产出释放事件。释放按
  **释放前最后一帧的占用状态**拆成三种：未开阀释放 / 淋浴后释放 / 暂停中释放——
  「本次淋浴 X 分钟」只对淋浴后释放成立。事件中文名取 `DoorState` 的目标状态正名
  （等待开阀 / 淋浴中 / 已暂停 / 空闲），不另造动词；选择界面按 分配 / 用水 / 释放
  三阶段分组勾选，创建按「设备 × 学号 × 事件」三轴展开。
- **文本是模板，占位符只有事件自带的事实**：规则存模板，事件发生时用事件值
  （喷头号 / 学号 / 目标状态）渲染成最终文本再合成/缓存；播报不依赖会话表。可靠
  占位符只有 `{door_no}` / `{cert_no}` / `{event}`（学号逐位念、可 `{cert_no:N}`
  截断）。曾有时长两个占位符（`{assigned_duration}` / `{shower_duration}`）：取值
  随会话变化、永不命中音频缓存、每场都要现场合成，已移除——播报以预热的固定音频
  为主。支付状态、金额、姓名没有可靠数据源，不做。
- **等待浴室 App 的提示音在设备端完成**：浴室 App 的分配/结算提示是 `MediaPlayer`
  播的预录音频，走 `STREAM_MUSIC`；本应用播报走 `STREAM_VOICE_CALL`，两边都不抢
  音频焦点，同时播就会混在一起。设备在播放前用 `AudioManager.isMusicActive()` 检测
  浴室提示音，等它结束再开口；最长等待由 `voice_bath_wait_max_ms` 控制，超时照常播放
  并记 `audio.bath-wait-timeout`。规则不再有逐条的 `delay_ms`；服务端合成完即下发，
  各阶段耗时（音频准备 / 事件到下发 / 下发到播完 / 是否现场下载）仍写入
  `voice_delivery` 并在网页「最近推送」展示。自动结算/续期/延长服务产生的释放与
  重新分配仍按事件处理，靠规则配置规避重复，不另设来源抑制。
- **手动推送与自动触发共用一条投递链，来源由事件键区分**：管理台的「推送」按规则
  同一条渲染/合成/下发路径真播一遍。投递记录不另存来源列：`manual:*` 事件键已经是
  「谁发起」的身份，页面据此显示自动触发或手动推送。
- **音色与合成参数是全局配置并共同构成音频身份**：音色（`voice_model`，medium /
  x-low 两个 Piper 中文模型）、语速、语调起伏、音长抖动、句间停顿全部写进音频的
  配方标识——改任何一项都生成新文件、旧缓存按最近使用淘汰，不存在新参数读到旧
  音频的组合。参数按「配置键一档、换算一处、门禁对账」的形状落在 config/spec.py
  与 tts.py 两处。
- **音效与停顿是模板里的占位符，不是独立字段**：`{fx:名称}` 在该位置插入音效库里的
  音效（只响不读），`{pause:毫秒}`（100–5000）插入静音——位置与间隔完全由模板表达。
  合成按段拼 WAV（语音段各跑一次 Piper、音效重采样对齐、停顿补零），一次性编码成
  MP3，设备拿到的是一段普通音频，端侧零改动。音效名被任何模板引用时禁止删除
  （停用的规则随时会再启用），不做静默少播。**改名不受引用限制**：改名时把引用它的
  规则模板里的 {fx:旧} 级联改写为 {fx:新}，规则不失效；音效名全库唯一（创建/改名都会
  拒绝重名），否则 {fx:名} 指不出是哪一个。
- **离线不播、不排队、不补播**：事件超过 `voice_event_max_age_s`（默认 60 秒）就跳过；
  同一事件用 `event_key` 只认领一次。动态模板的音频按最终文本缓存，服务端与设备端都有
  容量上限与最旧淘汰。
- **设备走 `STREAM_VOICE_CALL`**：本机实测只有这条流在主输出上有非零音量（4/5），
  Media/TTS 流为 0；播放前保存并设置该流音量，结束/失败/超时后恢复，进程被杀时由本地
  待恢复标记在下次启动时补恢复。设备日志用 `audio.*` 事件名，`voice.*` 只留给命令失败原因码。

## OTA 与版本

- **发布声明必须与 APK 内容版本一致，发布边界强制比对**（2026-10-24 事故的根除项）：
  发布接口解析 APK 的二进制 manifest（`ota/apk_manifest.py`，零依赖的最小 AXML 解析），
  声明 0.4.40 而字节是 0.4.39 的发布曾被照单全收——设备端 `pm install` 返回 Success 而
  版本不变，manifest 永远"有新版"，六台设备陷入无限重装循环。`-SkipBuild` 带着陈旧
  构建产物发布正是那条路。设备端配套两道：安装脚本**不再删除尝试锁**（锁在则重试被
  退避挡住），同一版本尝试三次后停手并在 device.log 留 `ota.attempts-exhausted`，
  等人工而不自愈——自愈的前提是发布正确，发布不正确时自愈就是循环本身。
- **版本号在三处，由测试强制一致**：`server/app/core/version.py` 的 `APP_VERSION`、
  `server/pyproject.toml` 的 `version`、`android/app/build.gradle.kts` 的 `versionName`，
  由 `tests/test_version_consistency.py` 校验。**这三处合并不了**——前两个是 Python 侧（一个
  供运行时、一个是包元数据），第三个在 Kotlin 构建脚本里，跨语言没有共享一处的办法，测试是
  唯一手段。OTA 覆盖安装要求新旧版本可比，人工同步必然出错。
- **APK 用正式证书一步到位签名，不用调试签名过渡**。自更新要求新旧 APK 签名一致，调试签名
  一旦上机就切不回来。证书与密钥的位置、参数、指纹见 `docs/ARCHITECTURE.md`「签名」；
  它是全系统唯一长期绑定物件——丢失意味着所有在网设备都要物理接触重装。异地备份的做法见
  `docs/RUNBOOK.md`。
- **自更新链路全自动**：设备按配置间隔轮询 `/ota/manifest`，下载后校验 sha256 再 `pm install`，
  覆盖安装由 `MY_PACKAGE_REPLACED` 广播自启（该广播在 stopped 状态也送达，真机验证过）。
  升级零现场。
- **发布是推送加轮询双通道**：发布即向在线目标设备推 `ota.upgrade_available`，离线设备靠轮询
  自然补齐；`target` 支持逗号分隔的定向列表。调试期 `force` 发布无视版本号，只更新指定设备。
- **安装状态在服务端跟踪**：设备 `link.hello` 里的 `version_code` 即安装确认，
  `ota_release_install` 表记录到该版本为止；已确认的 `force` 发布不再推，重推同一版本需先调
  `POST /api/v1/ota/releases/{version}/rearm/{device_id}`，`DELETE /api/v1/ota/releases/{version}` 用于
  紧急下架。缺少这层跟踪会让 force 发布与设备重启构成无限重装循环——真机发生过一次。
- **发布按个数保留（`ota_release_keep`，默认 5）**：新版登记时裁最旧的，注册行与 APK
  文件一起删。留的是回滚点而不是历史档案——盘上的旧 APK 只有体积没有意义；N=1 会让
  "新版有问题退回上一版"无处可退。
- **删除接口连文件一起删**：`DELETE /api/v1/ota/releases` 只删注册行会让 APK 变成无人认领的
  孤儿文件，"下架"的语义必须覆盖到盘上那份。

## 可观测性

> 标准依据：OWASP Logging Cheat Sheet（记什么、不记什么）、NIST SP 800-92
> （审计记录的生成/保护/保留）、W3C Trace Context（关联标识）、OpenTelemetry
> Log Data Model（字段命名）。2026-10-01 采纳。

- **三层痕迹，一条链**：`api_call`（HTTP/网关审计）→ `command_audit`（命令级审计）
  → 设备端 `audit.log`（命令痕迹 JSONL），以 `command_id` 与 `trace_id` 贯通——
  "这个命令服务端发给谁、设备收到没有、结果是什么"在三个层面各有一行可查。
- **审计记什么**：全部 /api、/ops、/ota 请求（认证失败、授权失败、参数不合法、
  服务端错误天然落表，OWASP 的必记事件类）；设备网关的连接与断开（含设备来源 IP）。
  不记静态资源与 /healthz；发布上传的 APK 二进制体不落库（本体已存 ota_releases，
  审计行记版本与大小即完整事实）。
- **如实记录、不脱敏、不截断**（2026-10-01 用户决定，覆盖同日早先的脱敏决定）：
  本系统是单运维者工具，审计的价值就在于如实——调用方令牌、身份、来源 IP、
  User-Agent、请求体原文**全文落库**；`device.exec` 的输出（不可重现的运维事实）
  随命令审计落 `data` 列。媒体（截图/拍照的 base64）与可重取的 `ui.dump` XML
  仍不落库——那是体积与时效取舍，不是脱敏。
- **两个审计分类的分工**：`api_call`（接口调用）记"每一次后台请求——谁、从哪个
  IP、调了什么、结果如何"；`command_audit`（命令流水）记"每条发到设备的命令——
  参数、结果、设备回报"。**必要分开**：命令是"先登记、结果异步回填"的两段式
  生命周期，与一次写完的请求行形状不同；合并会得到一张两边都缺列的稀疏表。
  前端用标签切换并以 tooltip 写明各自职责。
- **stdout 日志是 JSON 事件流**（12-Factor §XI）：一行一个对象，字段照 OTel
  Log Data Model（`ts`/`level`/`logger`/`message`/`event`），`trace_id`/
  `request_id` 有值才输出。`event` 是给机器检索的稳定代号（kebab-case），与
  中文 `message` 分开——改文案不能破坏检索；属性只收标量。不写文件、不做轮转，
  归档是运行环境的职责。
- **HTTP 与命令的关联**：W3C `traceparent`（调用方带就沿用其 trace-id，否则生成），
  响应回 `X-Request-ID`；问题响应经 `X-Problem-Type` 头把 RFC 9457 type 带进审计行。
  命令派发时把 trace_id 写进 `command_audit`——跨层查一次 SQL 就是全链路。
- **保留期执行而不是声明**：审计两表（`api_call` 与 `command_audit`）按
  `audit_retention_days`（默认 90 天）由每日任务删除——审计是滚动窗口；**业务
  数据（喷头状态迁移、使用会话）永久保留**，那是运营历史。OTA 发布按
  `ota_release_keep`（默认 5 个）在新版登记时裁剪。
  设备端落盘文件全部有界且集中：`/sdcard/ntu-shower/` 下 device.log（统一日志，
  见下）/ crash.log / automation.log 各 256KB 封顶、ota-install.log（脱手脚本
  唯一可写通道）每次安装截断、OTA 下载包装完即删、outbox 按行数上限裁剪、
  shell pid 文件正常完成与超时两条路径都自清。敏感数据（发件箱含学号）在应用
  私有目录 `/data/data/<包名>/databases/agent.db`，共享存储上无敏感内容。
- **设备端统一日志（core.log.DeviceLog）**：全设备唯一结构化落盘入口——一个类、
  一个文件（device.log，JSONL）、一种格式，事件名与服务端 log_event 同族
  （command.* / gateway.* / service.* / config.* / ota.*）。服务生命周期、配置
  变更、命令痕迹、网关状态全部经它落盘；敏感红线（学号/密码/令牌/剪贴板内容
  永不入日志）写入类注释作为硬约定。看门狗闹钟用 setExact 逐次排（4.4 的
  setRepeating 有不可纠正的批处理漂移；setExactAndAllowWhileIdle 要 API 23）。
- **设备端痕迹是文件而不是 Logcat**：Logcat 环形缓冲重启即空，而"命令收到没有、
  回了什么"是远程排障的第一直觉；`/sdcard/ntu-shower/audit.log` 用 `device.exec`
  直接 `cat` 取回。

## 测试与质量

- **门禁是机器强制，不靠自觉**，且本地与 CI 跑同一组命令——命令清单见 `README.md`「质量门」
  与 `.github/workflows/ci.yml`（两者逐条对应），此处不复述。
- **两端都设覆盖率门，并配赦免清单**：能抽成纯逻辑覆盖的必须覆盖，只有真正无法在 JVM 上覆盖
  的类才排除。设备端豁免登记在 `android/app/build.gradle.kts` 的 `frameworkBoundClasses`，
  逐条带理由；门槛只升不降，加豁免要解释为什么抽不出纯逻辑。
- **覆盖率与测试数不写进文档**，由 CI 实时产出。文档里写死的数字必然过期。
- **结构约束也进测试**，而不只测行为：协议 schema、动作名集合、失败原因码、配置键对账、
  静态挂载顺序、版本一致性都有对应的执行机制。约束只写在文档里，等于没有。

## 部署与入口

- **443 统一入口，nginx 按路径分流**，服务器只暴露 80/443/22。证书一张、防火墙规则最少；
  代价是 nginx 进入关键路径。
- **域名 `ntu-shower.iseekdream.com`，单张通配符证书**。设备实测支持 ECDHE-ECDSA（见
  `docs/ARCHITECTURE.md`「已定稿的传输层事实」），所以旧系统为迁就 4.4 而维护的 RSA 证书
  不再需要；续期依赖 Let's Encrypt。
- **网页端是零构建静态文件**（`server/web/`），由服务端本身托管在根路径，合并了旧系统的调试
  面板与画面查看器。改完刷新即可，无编译步骤、无框架版本约束、与 API 同源无跨域。
  曾试过 Taro + React 的跨端方案，两个页面的规模撑不起它的接入成本，工程已删除；
  服务端契约为任何前端保留。
- **`mount("/")` 必须在所有路由之后注册**：Starlette 按注册顺序匹配，提前挂载会让 `/api`、
  `/ops`、`/ota`、`/gateway` 全部变成静态文件查找并返回 404。顺序由 `test_e2e_branches.py`
  锁定。
- **前端资源响应带 `Cache-Control: no-cache`**（`.html`/`.js`/`.css`）：浏览器每次都带 ETag
  回来验，未变即 304。没有它时只有 `Last-Modified`，浏览器会走启发式缓存，改完样式刷新看到的
  还是旧的那一份。
- **真实 ADB 经 443 网关透传，零新端口、零新进程**：管理面
  `POST /api/v1/devices/{device_id}/bridge/open` 下发含一次性 nonce 的 `bridge.open`，设备以 root 打开
  adbd 并另开一条二进制 WSS 与本地 adbd 互泵字节流；服务端 nonce 配对后绑 `127.0.0.1:<port>`
  （15655 起，避开旧系统的 15555），开发者经 SSH 转发后 `adb connect`。保留真实 adb 的完整
  能力（shell/install/dumpsys），不用轻量替代。
- **桥的约束**：仅管理面可触发、一次性 nonce、仅绑回环、TCP 断开不拆桥（回到等待下一个连接）、
  空闲 300 秒回收。依据是 Root Bridge 事件（裸 ADB 暴露公网导致大规模失陷）：adb 字节流全程
  在 WSS/TLS 内，不对外网开放任何端口。
