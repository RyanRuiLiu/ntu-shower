# 文案与术语

**同一件事在每一端只有一个叫法。** 设备端与服务端的代码标识与用户文案都以此表为准。
前端是独立工程（不在本仓库），接入时同样遵循本表。

## 为什么需要这张表

同一个概念在不同地方叫不同名字，是维护成本最低调的来源：用户听不懂、开发者搜不到、
翻译时对不上。本项目已经出现过「版本发布 / OTA 发布 / releases」三种说法指同一功能。

## 两套词：代码标识 vs 用户文案

**代码标识一律英文**（变量、函数、API 字段、数据库列、消息类型），
**用户文案一律中文**。这不是翻译关系，而是两层各自的要求：

- 代码标识是**机器与跨语言协作者的接口**——英文是行业事实标准
- 用户文案是**学生看到的字**——必须是他日常会说的话

两者不必一一对应。例如 `door` 在代码里指"一个淋浴位"，对学生就是**喷头**。

## 术语表

| 概念 | 代码标识 | 用户文案 | 备注 |
|---|---|---|---|
| 一个淋浴位 | `door`、`door_no` | **喷头** | 浴室 App 的表叫 `t_doorlist`，字段 `doorNo`；但学生说的是"喷头"，不是"门" |
| 分配（开始使用） | `assign`、`session.assign` | **分配** | 沿用旧系统与浴室 App 的说法 |
| 结算（结束使用） | `settle`、`session.settle` | **结算** | 同上 |
| 拍照 | `photo`、`photo.capture` | **拍照** | |

| 一台浴室终端 | `device`、`device_id` | **设备** | 面向管理员时的说法 |
| 设备的连接状态 | `online` | **在线 / 离线** | |
| 可以操作喷头的身份 | `capability: ops`、`grant` | **权限** | 管理端说"授权名单" |

## 喷头的七个状态

服务端 `DoorState` 的取值与展示文案。**设备端不显示状态**（无界面），
因此这一列只有服务端与前端。

| 代码值 | 展示文案 | 含义 |
|---|---|---|
| `free` | 空闲 | 可以立刻使用 |
| `waiting` | 已入门 | 已刷卡进入，尚未出水 |
| `bathing` | 使用中 | 正在出水 |
| `paused` | 已暂停 | 出水后暂停，会话未结束 |
| `selected` | 选中 | 被界面选中但未开始使用 |
| `repair` | 报修 | 设备标记为待维修 |
| `disabled` | 禁用 | 设备标记为停用 |

## 错误文案：服务端直接给可展示的中文

服务端的 RFC 9457 响应三个成员各司其职：

| 成员 | 语言 | 给谁看 |
|---|---|---|
| `type` | 英文 code | **机器**——客户端据此分支，是唯一稳定的字段 |
| `title` | **中文** | **人**——该问题类型的稳定简述，可直接展示 |
| `detail` | **中文** | **人**——本次请求的具体信息，可直接展示 |

**服务端直接给出可展示的文案，调用方原样显示**：

```
展示顺序：detail（更具体） → title（类型简述） → 本地兜底（网络层失败时）
```

**不要在客户端维护映射表。** 曾经写过一层「按 `type` 映射中文」，那是多余复杂度：
同一句话会在服务端和前端各定义一次，改一处忘另一处就漂移。文案的归属是
服务端——它知道发生了什么，客户端不知道。

`title` 用中文而不是英文，理由同样是简单：它按 RFC 9457 的定义就是"人类可读
的摘要"，而本系统的使用者是中文用户。写成英文再让客户端翻译，等于凭空造一层。

## 写作原则

- **说用户会说的话**。"喷头正在使用中"而不是"门状态非空闲"
- **主动语态，动作即结果**。按钮写「分配」，成功后提示「已分配」
- **错误说清是什么**，不道歉、不含糊。"设备离线"而不是"操作失败"
- **不用技术词面向用户**。`capability` → 权限；`OTA` → 版本发布；`ADB` → 调试通道
- **空状态是行动指引**。"设备尚未上报喷头状态" 比 "暂无数据" 有用
